как быть с аннотациями функций, тип возвращаемых значений которых зависит от значений параметров? Именно от значений, а не от типа данных входных параметров. В этом посте постараюсь развернуто ответить на этот вопрос.

В качестве функции, тип возвращаемого значения которой зависит от значений аргументов, возьмем функцию подмодуля pyplot библиотеки Matplotlib - subplots. У этой функции есть два опциональных аргумента: nrows=1 и nclos=1. Эти аргументы задают число строк и число колонок с графиками. Если значения обоих аргументов равны 1, то возвращаемое значение будет иметь тип tuple[Figure, Axes]. Если же значение хотя бы одного из этих параметров будет отличаться от 1, тип возвращаемого значения будет варьироваться от tuple[Figure, numpy.array] до tuple[Figure, Any] в зависимости от значений других параметров. И эта функция аннотирована (во всяком случае в версии matplotlib==3.10.3) так:
# matplotlib/pyplot.py
@overload
def subplots(
    nrows: Literal[1] = ...,
    ncols: Literal[1] = ...,
    # другие параметры
) -> tuple[Figure, Axes]:
    ...

@overload
def subplots(
    nrows: int = ...,
    ncols: int = ...,
    # другие параметры
) -> tuple[Figure, np.ndarray]:
    ...

@overload
def subplots(
    nrows: int = ...,
    ncols: int = ...,
    # дрегие параметры, но со значениями по умолчанию
) -> tuple[Figure, Any]:
    ...

Что тут происходит? Ну, во-первых, тут используется декоратор overload - полезная штука для "перегрузки" аннотаций типов. Причем реализация функции будет одна, вся логика будет в ней. А аннотаций у нас аж 3 штуки - на каждый важный для нас случай. Это сделано для удобства. Так IDE сможет делать нужные подсказки сигнатуры в зависимости от того, как вы работаете с функцией, а статический анализатор типов будет полагаться на эту перегрузку при проверки вашего кода. Во-вторых, для того, чтобы реализовать зависимость типа возвращаемого значения от значений аргументов, в первой перегрузке используется аннотация Literal[1]. Если значения аргументов будут равны 1, в качестве аннотации будет использован первый вариант из приведенного выше листинга.

Казалось бы, красота. Ведь так? К сожалению, нет. Вот есть у меня такой листинг кода:
import matplotlib.pyplot as plt

if __name__ == "__main__":
    nrows = 1
    figure, axis = plt.subplots(nrows=nrows)
    reveal_type(figure)
    reveal_type(axis)

Фактически, тут реализуется первый вариант вызова, когда значения nrows и nclos равны 1. Но MyPy и IDE думают иначе:
$ mypy .\test_subplots.py
test_subplots.py:7: note: Revealed type is "matplotlib.figure.Figure"
test_subplots.py:8: note: Revealed type is "Any"

С точки зрения MyPy данные переменной axis имеют тип данных Any, а не Axes. Происходит это потому что nrows - это не литерал. С точки зрения статического анализатора типа в nrows могут лежать любые целочисленные данные. Значение этой переменной может неоднократно поменяться до того момента, когда она фактически будет использована в вызове plt.subplots. Поэтому с точки зрения MyPy первую аннотацию из предыдущего листинга тут использовать нельзя, а нужно использовать более подходящий вариант. Вариант с Any подходит больше из-за значений других параметров, которые мы опустили в нашем примере.

Чтобы все работало как планировалось, мы можем использовать в вызове литерал: plt.subplots(1). Или мы можем явно дать понять MyPy, что значение переменной nrows меняться не будет: nrows: Final[int] = 1. Оба варианта имеют свои слабые места. В первом случае код становится менее читаемым из-за использования магической константы. И хотя передача значения в именованном стиле может компенсировать этот недостаток, мы все равно не сможем нигде переиспользовать это значение. Во втором случае мы связываем себе руки. Теперь мы не можем изменять значение nrows, иначе нам придется иметь дело с ошибкой статического анализа типов.
