# Анотації типів в Python

Анотації типів в Python — це спеціальний синтаксис, який дозволяє вказувати очікувані типи для змінних, параметрів функцій та значень, що повертаються функціями. 

Важливо розуміти, що **Python залишається мовою з динамічною типізацією**. 
Анотації типів за замовчуванням **не перевіряються під час виконання програми** і не змінюють поведінку інтерпретатора Python. 
Їх основна мета — надати підказки для статичних аналізаторів коду (таких як MyPy, Pyright, Pytype) та покращити досвід розробки в IDE.

**Приклад простої анотації:**

```python
def greet(name: str) -> str:
    return f"Hello, {name}"

user_name: str = "Alice"
greeting_message: str = greet(user_name)

print(greeting_message)
```

У цьому прикладі:

- `name: str` вказує, що параметр `name` функції `greet` очікує рядок.
- `-> str` вказує, що функція `greet` повертає рядок.
- `user_name: str` та `greeting_message: str` анотують змінні як рядки.

Використання анотацій типів приносить численні переваги, які суттєво підвищують якість розробки:

#### Покращення читабельності коду

Анотації роблять код більш зрозумілим, оскільки вони явно документують очікувані типи даних. 
Це схоже на **внутрішні підказки**, 
які допомагають іншим розробникам (і вам у майбутньому) швидше зрозуміти, як правильно використовувати функції та класи.

Без анотацій:

```python
def process_data(data, config):
    # ... що таке data? Якого типу config?
    pass
```

З анотаціями:

```python
from typing import List, Dict, Any
def process_data_typed(data: List[Dict[str, Any]], config: Dict[str, Any]) -> bool:
    return True
```

Тепер набагато зрозуміліше!

- `data` - це список словників
- `config` - це словник
- функція повертає булеве значення


#### Раннє виявлення помилок

Це одна з найважливіших переваг. 
Статичні аналізатори типів використовують анотації для перевірки коду **перед його виконанням**. 
Вони можуть виявити помилки, пов'язані з типами, такі як передача аргументу неправильного типу у функцію або використання методу, якого немає у певного типу. 
Це дозволяє **локалізувати та виправляти помилки значно раніше**, на етапі написання коду, що економить час та зусилля на налагодження.

```python
def add_numbers(a: int, b: int) -> int:
    return a + b
```

Статичний аналізатор (наприклад, MyPy) попередить про помилку тут:

```python
result = add_numbers(5, "hello") # Error: Argument 2 to "add_numbers" has incompatible type "str"; expected "int"
```

#### Підтримка інструментами розробки (IDE, лінтери)

Сучасні IDE (VS Code, PyCharm тощо) та лінтери активно використовують анотації типів. 
Це **дозволяє IDE розуміти, які типи даних ви очікуєте**, що призводить до:

*   Кращого автодоповнення коду.
*   Точніших підказок щодо параметрів функцій.
*   Ефективнішого рефакторингу.
*   Миттєвого підсвічування помилок типів безпосередньо в редакторі.

Коли ви змінюєте частину коду, анотації типів допомагають переконатися, що ваші зміни не порушують контракти типів в інших частинах системи. 
Це робить рефакторинг безпечнішим та менш схильним до помилок. 
Для великих проектів та команд це критично важливо для довгострокової підтримки коду.

Анотації слугують чіткою документацією інтерфейсів між різними частинами коду, 
що полегшує взаємодію між розробниками та інтеграцію їхньої роботи.

### Анотації типів не впливають на виконання коду Python (за замовчуванням)

Ще раз наголосимо: стандартний інтерпретатор Python **ігнорує анотації типів під час виконання**. Вони не перетворюють Python на мову зі статичною типізацією, як Java або C++.

```python
def process_value(value: int) -> None:
    print(f"Value is {value}, its type is {type(value)}")

process_value(10)       # Output: Value is 10, its type is <class '''int'''>
process_value("hello")  # Output: Value is hello, its type is <class '''str'''>
```

Жодної помилки під час виконання через невідповідність типу!

Однак, існують інструменти та бібліотеки, які можуть використовувати анотації типів під час виконання. Наприклад:

*   **Pydantic**: Використовує анотації для валідації даних та серіалізації/десеріалізації.
*   **FastAPI**: Веб-фреймворк, який сильно покладається на Pydantic та анотації типів для валідації запитів, генерації документації API тощо.
*   **Beartype**: Бібліотека, що забезпечує перевірку типів під час виконання на основі анотацій.

Ці інструменти розширюють можливості анотацій, але основна їхня мета залишається статичним аналізом та покращенням процесу розробки.

### Коротка історія

Концепція анотацій типів була офіційно введена в Python з версії 3.5 через **PEP 484 ("Type Hints")**. Цей PEP заклав основи синтаксису та семантики для анотацій функцій, а також представив модуль `typing`.

З того часу спільнота Python активно розвивала систему типізації, що призвело до появи низки інших важливих PEP:

*   **PEP 526 ("Syntax for Variable Annotations")**: Введено в Python 3.6, додав синтаксис для анотування змінних (наприклад, `my_var: int = 10`).
*   **PEP 544 ("Protocols: Structural subtyping (static duck typing)")**: Введено в Python 3.8, дозволяє визначати "протоколи" – класи, що описують інтерфейс на основі наявності певних методів та атрибутів (структурна типізація).
*   **PEP 561 ("Distributing and Packaging Type Information")**: Стандартизує спосіб розповсюдження інформації про типи для пакетів, дозволяючи статичним аналізаторам перевіряти код, що використовує сторонні бібліотеки.
*   **PEP 563 ("Postponed Evaluation of Annotations")**: Введено в Python 3.7 (стандартна поведінка з `from __future__ import annotations`, планувалося за замовчуванням у Python 3.10, але відкладено). Дозволяє використовувати імена типів, які ще не визначені, шляхом обробки анотацій як рядків під час компіляції. Це вирішує проблеми з прямими та зворотними посиланнями.
*   **PEP 585 ("Type Hinting Generics In Standard Collections")**: Введено в Python 3.9. Дозволяє використовувати вбудовані типи колекцій (такі як `list`, `dict`, `tuple`) як генерики безпосередньо, замість імпорту їхніх аналогів з модуля `typing` (наприклад, `list[int]` замість `typing.List[int]`). Це значно спрощує написання анотацій.
*   **PEP 586 ("Literal Types")**: Введено в Python 3.8 (через `typing.Literal`). Дозволяє вказувати, що змінна може мати лише одне з декількох конкретних літеральних значень.
*   **PEP 589 ("TypedDict: Type Hints for Dictionaries with a Fixed Set of Keys")**: Введено в Python 3.8 (через `typing.TypedDict`). Дозволяє визначати типи для словників з фіксованим набором рядкових ключів та типами значень для кожного ключа.
*   **PEP 591 ("Adding a final qualifier to typing")**: Введено в Python 3.8 (через `typing.Final` та `typing.final`). Дозволяє позначати змінні, атрибути або методи як фінальні, тобто такі, що не можуть бути перепризначені або перевизначені.
*   **PEP 604 ("Allow writing union types as X | Y")**: Введено в Python 3.10. Надає більш чистий та інтуїтивний синтаксис для об'єднання типів за допомогою оператора `|` замість `typing.Union`.
*   **PEP 612 ("Parameter Specification Variables")**: Введено в Python 3.10 (через `typing.ParamSpec` та `typing.Concatenate`). Дозволяє анотувати параметри функцій вищого порядку та декораторів, зберігаючи інформацію про типи параметрів функції, що декорується або передається.
*   **PEP 613 ("TypeAlias")**: Введено в Python 3.10 (через `typing.TypeAlias`). Надає явний спосіб оголошення псевдонімів типів, що покращує читабельність для статичних аналізаторів.
*   **PEP 646 ("Variadic Generics")**: Введено в Python 3.11 (через `typing.TypeVarTuple`). Дозволяє створювати генерики з довільною кількістю параметрів типу, корисно для анотування таких бібліотек, як NumPy.
*   **PEP 647 ("User-Defined Type Guards")**: Введено в Python 3.10 (через `typing.TypeGuard`). Дозволяє створювати функції, які звужують тип змінної в певній гілці коду.
*   **PEP 655 ("Marking individual TypedDict items as required or potentially-missing")**: Введено в Python 3.11 (через `typing.Required` та `typing.NotRequired` в `TypedDict`).
*   **PEP 673 ("Self Type")**: Введено в Python 3.11 (через `typing.Self`). Дозволяє легко анотувати методи, які повертають екземпляр свого класу (наприклад, у конструкторах або фабричних методах).
*   **PEP 675 ("Arbitrary Literal String Type")**: Введено в Python 3.11 (через `typing.LiteralString`). Дозволяє вказувати, що рядок є літералом, корисним для SQL-запитів або shell-команд для запобігання ін'єкціям.
*   **PEP 681 ("Data Class Transforms")**: Введено в Python 3.11 (через `typing.dataclass_transform`). Дозволяє декораторам або метакласам повідомляти статичним аналізаторам, що вони трансформують клас подібно до `@dataclasses.dataclass`.
*   **PEP 695 ("Type Parameter Syntax")**: Введено в Python 3.12. Представляє новий, більш компактний синтаксис для оголошення генеричних класів, функцій та псевдонімів типів.
*   **PEP 702 ("Marking parameters as @typing.override")**: Введено в Python 3.12 (через `typing.override`). Дозволяє явно позначати методи, які перевизначають методи батьківського класу, допомагаючи виявляти помилки при рефакторингу.

Цей розвиток показує, наскільки важливою стала система типізації для екосистеми Python.
